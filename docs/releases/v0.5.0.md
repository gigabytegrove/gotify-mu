# Gotify MU v0.5.0

**Status:** Preview candidate  
**Release date:** 2026-09-25

Gotify MU v0.5.0 is the security, reliability, integration, collaboration, plugin, and operations completion release following the v0.3 native-automation preview.

It keeps the existing Gotify REST/WebSocket and application/client-token compatibility model while substantially expanding the Gotify MU server and Web UI.

## Security

v0.5 introduces:

- encrypted at-rest storage for protected integration, connector, MFA, and related server secrets
- login throttling and security-event auditing
- TOTP MFA and hashed recovery codes
- WebAuthn/passkeys
- LDAP / Active Directory authentication
- configurable local/OIDC/LDAP authentication coexistence
- scoped service accounts/API credentials
- active-session visibility and revocation
- configurable session/elevation/security policy
- sensitive path, query-string, updater-error, and audit-request redaction
- signed/checksummed plugin verification with trusted Ed25519 signing keys
- inbound Webhook signing, replay prevention, source CIDR controls, and per-route rate limiting

The persistent secret-encryption key is created in the data directory with restrictive permissions unless an administrator supplies a stable key using `GOTIFY_MU_SECRET_KEY` or `GOTIFY_MU_SECRET_KEY_FILE`.

## Channels and collaboration

v0.5 adds:

- Owner / Manager / Publisher / Member / Read Only Channel roles
- Group-to-Channel assignment
- replies and message threads
- reactions
- mentions
- assignment / ownership of work
- resolve and reopen state
- per-user read state
- attachments
- reusable message templates
- saved message searches
- richer acknowledgement state and acknowledgement history

These fields remain additive. Existing Gotify clients may ignore Gotify MU-specific collaboration data and continue normal notification reception.

## Notification automation

The automation engine now includes:

- multi-instance scheduler leases
- idempotent scheduled delivery
- one-time, hourly, daily, weekly, and cron schedules
- excluded dates
- maximum-run counts
- end dates
- misfire policies
- schedule execution history
- Quiet Hours suppression or deferred delivery
- stored Digest summaries
- configurable Digest intervals and immediate-priority bypass
- Escalation targets for Channels, users, and Groups
- repeat escalation behavior
- structured escalation parent/root relationships
- acknowledgement-based cancellation
- escalation loop/depth protection
- cleanup/retention for completed automation state

## Webhook Router

Inbound Webhooks support:

- generated secret URLs
- encrypted secret storage and hashed lookup
- optional HMAC-SHA256 request signing
- timestamp/replay protection
- source IP/CIDR restrictions
- configurable per-source rate limiting
- a one MiB payload limit with explicit rejection
- JSON title/message/priority field extraction
- array-aware dotted paths such as `items.0.name`
- conditional field/value matching
- title and message templates
- raw-body template insertion
- retained delivery history showing delivered, ignored, rejected, rate-limited, and failed requests

Webhook history stores diagnostic metadata, not full request payloads or credentials.

The Docker Compose deployment binds SMTP and Syslog receiver ports to loopback by default. Administrators must deliberately set `GOTIFY_MU_RECEIVER_BIND` to a trusted host/LAN address when remote devices need access.

## Plugins

The plugin platform now includes:

- administrator verified upload/install
- SHA-256 checksum validation
- Ed25519 signature verification
- administrator-configured trusted signing keys
- unsigned installs disabled by default
- Plugin Catalog support
- catalog install/update
- verified manual update staging
- uninstall
- plugin notifications routed through normal Quiet Hours/Digest/Escalation delivery policy

Native Go plugins execute in the Gotify MU server process and therefore remain trusted extensions rather than sandboxed code. Only install plugins from trusted publishers.

## Managed updates

The updater now:

- resolves the exact numbered release
- downloads the published source archive
- verifies it against published SHA-256 checksums
- runs the complete server test suite during the release build
- preserves current runtime settings when replacing the container
- redacts sensitive environment values from command failures
- requires the replacement image to pass its real Docker health check
- restores the prior application container automatically on failed replacement/startup verification

Database rollback after a migration still requires restoration of the corresponding pre-upgrade data backup. See `docs/DEPLOYMENT.md`.

## Preview validation requirements

Do not publish v0.5.0 solely because the feature implementation is complete.

The release candidate must still pass:

1. the current PR verification workflow from start to finish
2. the complete Web UI build
3. the full Go test suite
4. lint and repository consistency checks
5. the production Docker build with tests enabled
6. vulnerability gates
7. database migration against the existing test deployment
8. green application and database health
9. existing application/client-token compatibility tests
10. live Webhook, MQTT, Home Assistant, connector, automation, security, collaboration, plugin, backup/restore, and updater smoke checks

Keep the pre-upgrade container and verified data backup until the v0.5 preview has completed live validation.
