# Gotify MU v1.0.2

Gotify MU 1.0.2 simplifies both deployment and the Software Update experience.

## Single-container deployment

A normal Gotify MU installation now has exactly one persistent Docker container:

```text
gotify-mu
```

There is no permanent `gotify-mu-updater` service.

The application container has access to the Docker socket and includes the internal one-shot update worker. When an administrator starts an update, Gotify MU launches a short-lived worker from the currently running Gotify MU image. That worker performs the verified replacement and exits when the update finishes.

After the update completes, the only persistent Gotify MU container is again `gotify-mu`.

## Software Update

**Settings → Software Update** now focuses only on the update workflow:

1. Check GitHub for the latest published release.
2. Click **Install**.
3. Watch the current update stage and progress percentage.
4. Gotify MU replaces and verifies the application container.
5. The interface reloads into the installed release.

The Download files section, individual release asset buttons, release-note button, persistent updater status badge, and verbose activity log have been removed from this screen.

## Safety retained

The simpler interface does not remove update safety:

- published source package and SHA-256 verification
- full application tests during the replacement build
- preservation of persistent application data and runtime configuration
- health verification before accepting the replacement
- automatic restoration of the previous container when verification fails
- update progress persisted under `/app/data` across the container restart

## Docker socket

The recommended Compose deployment mounts `/var/run/docker.sock` into the Gotify MU container so the application can perform administrator-requested self-updates. Docker socket access is privileged host access and should only be granted to a trusted Gotify MU installation.
